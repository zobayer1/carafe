Carafe Architecture

A C++17 HTTP/1.1 server assembled from sockets upward. Three drawings: what the layers are, what owns what while a client is connected, and what happens between a connect and a response.

Four layers, and dependencies that only point down

The tree is split by what each part is allowed to know. net handles descriptors and syscalls and knows nothing about HTTP. http turns bytes into a request and never touches a socket. server joins the two and adds the policy: deadlines, routing, a bounded pool. Only the top band is installed; everything below it lives in src/ and is reachable solely through App.

What owns what, for as long as a client is connected

Ownership is the part worth getting right, because it decides what a failure destroys. One router is shared by every worker and never changes after registration. One pool exists for the whole run. Everything below a worker belongs to a single client and dies with it.

One request, from connect to response

The accept loop does as little as possible. It takes a descriptor, hands it over, and goes back to accepting, because anything it waits on is a wait every other client shares. Both rejections happen where they cost nothing: a full queue closes the socket on the accept thread without writing, and a connection that sat too long is dropped by the worker that finally reaches it.

What bounds each wait

BoundDefaultStartsWhat it protects
Deadlines::idle 30s each read between requests A worker held by a client that connected and then said nothing.
Deadlines::request 30s the first byte of a request A drip that would renew a per-read deadline for ever, and a response nobody collects.
PoolLimits::workers 64 construction Threads, so the count is chosen rather than discovered under load.
PoolLimits::queued 512 construction Memory and descriptors held by clients nobody has reached yet.
PoolLimits::queue_wait 5s the moment a socket is queued A worker spent on a client that gave up while it waited.
Every field is refused at zero. A zero deadline reaches setsockopt as no deadline at all, and a zero worker or queue count serves nobody, so App::run returns before it binds anything.

The reasoning behind each of these, and what was rejected on the way, is in docs/design-notes.md. The drawings show structure only: for what the server actually answers, examples/README.md has the measured transcripts.
